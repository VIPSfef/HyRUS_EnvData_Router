# Pixhawk 6C · PX4 v1.16.0 SHTC3 연결 진단

이 구성은 현재 실물 보드가 보고한 **PX4 v1.16.0**을 기준으로 `0x70` SHTC3 제품 ID·CRC를 확인할 진단 명령을 추가합니다. 연결선이 눈으로 맞아 보이지만 `i2cdetect -b 2`에서 주소가 나타나지 않는 경우, 일반 스캔과 제조사 통신 절차를 구분하기 위한 별도 펌웨어입니다.

**2026-10-25에 승인받은 진단 펌웨어를 실물 Pixhawk 6C에 설치하고, I²C 버스 2의 주소 `0x70`에서 SHTC3 제품 ID·CRC 확인에 성공했습니다.** 온습도 측정·정확도·실물 SENS_ATMOS/TCP 전송은 이번 검사 범위에 포함하지 않았습니다. 전압·풀업·핀 연결을 실제로 측정했다는 뜻도 아닙니다.

## 기준 버전과 변경 범위

- PX4 기준 커밋: `6ea3539157ca358c70a515878b77077af7d4611d`.
- 빌드 타깃: `px4_fmu-v6c_default`.
- 기존 `src/px4/shtc3/`의 공유 드라이버 6개 파일과 단발 제품 ID 조회 모듈을 추가합니다.
- 진단 전용 등록·보드 설정 패치는 이 디렉터리에 따로 보관합니다.
- 이 manifest는 `hardware` 프로필만 지원합니다.
- **기존 SENS_ATMOS·MAVLink dialect·SITL host I²C 패치를 적용하지 않습니다.** 그 경로는 다른 PX4 기준 버전에서 검증한 별도 구성입니다.
- 센서 드라이버와 진단 명령은 명시적으로 호출할 때만 사용합니다. 이 진단 패치는 `rc.sensors` 자동 시작을 추가하지 않습니다. 공유 소스의 YAML에 `SENS_EN_SHTC3` 기본값 0 정의가 있지만, 이번 실물의 파라미터 광고 목록에는 나타나지 않았습니다. 진단판은 자동 시작 hook 없이 수동 명령만 사용합니다.
- 기존 비행 파라미터·미션·센서 교정을 수정하는 명령을 실행하지 않았습니다. 업로드 전 설정 백업과 공식 복원용 펌웨어를 확보했습니다.

실물의 같은 버스 2에는 차압계 `0x28`과 SHTC3 `0x70`이 있어 주소가 겹치지 않습니다. 앞선 일반 `i2cdetect`는 `0x70`을 표시하지 않았지만, 이번 전용 제품 ID 읽기에는 성공했습니다. 따라서 그 스캔 미검출만으로 배선 불량이라고 볼 수 없습니다.

## 이번 실물 확인 결과

시동 해제 상태에서 `shtc3_probe -b 2`를 **한 번** 실행했습니다.

```text
result=MATCH stage=COMPLETE id=0x0887 crc_rx=0x5B crc_expected=0x5B operation_rc=0 sleep=OK sleep_rc=0
elapsed_us=4455
```

4,455 µs는 이번 한 번의 실행 시간이며 최악 실행 시간 보증이 아닙니다. SHTC3 지속 드라이버는 검사 전후 모두 실행하지 않았습니다. 같은 부팅 세션에서 차압계 읽기 수는 1,079→1,105로 증가했고 통신 오류와 fault 수는 각각 0→0이었습니다. 업로드 전 상태와 재부팅 후 상태를 섞어 무간섭을 주장하는 비교는 하지 않았습니다.

기존 파라미터 1,177개는 타입과 원시 wire 값이 모두 동일하고 누락이 없습니다. 새 광고 항목 `SENS_DPRES_REV` 하나가 확인되어 전체 광고 수는 1,178개이며, 이 항목은 `INT32` 값 0입니다. 관측값은 파일에 저장하지 않았고 마지막에 COM5를 해제했습니다. 상세 조건과 제한은 [검증 기록](VERIFICATION.md)에 있습니다.

## 안전하게 검사하고 적용하기

Python 3와 Git이 필요합니다. 다음 명령은 수집기 저장소 루트에서 실행하며 `PX4`는 **정확한 기준 버전의 별도 깨끗한 체크아웃**을 가리킵니다.

```sh
PX4=/path/to/PX4-Autopilot-v1.16.0
python3 support/px4/apply_overlay.py --px4 "$PX4" --manifest support/px4/pixhawk6c-v1.16-diagnostic/overlay-manifest.json --profile hardware --check
```

검사는 파일 해시·PX4 커밋·패치 문맥·기존 모듈 내용을 확인하고 임시 사본에서 적용 계획을 만듭니다. 실제 PX4 파일은 수정하지 않습니다. 검사 결과를 검토한 뒤 적용합니다.

```sh
python3 support/px4/apply_overlay.py --px4 "$PX4" --manifest support/px4/pixhawk6c-v1.16-diagnostic/overlay-manifest.json --profile hardware --apply
make -C "$PX4" px4_fmu-v6c_default -j4
```

적용 도구는 수정된 로컬 모듈을 강제로 덮어쓰지 않고, Git pull/reset·펌웨어 업로드를 실행하지 않습니다. 동일한 소스와 패치는 재적용해도 변경 0개가 됩니다. 기본 manifest가 다른 버전을 대상으로 하므로 **위의 `--manifest`와 `--profile hardware`를 생략하지 마세요.**

## 업로드 후 콘솔에서 한 번 확인하기

아래 명령은 진단 펌웨어가 설치된 보드의 QGC MAVLink Console에서 실행합니다. 기존 v1.16.0 원본 펌웨어에는 새 명령이 없습니다. 명령은 버스 번호를 필수로 받으며 다른 버스는 자동 탐색하지 않습니다.

```sh
shtc3 stop
shtc3_probe -b 2
```

첫 줄은 같은 센서의 지속 드라이버가 실행 중인 경우 중지하기 위한 것입니다. 실행 중이 아니면 `not running` 계열의 메시지만 나올 수 있습니다. 이 단발 조회는 온습도 변환이나 uORB 발행을 하지 않습니다. 버스 2가 실제 연결 버스인지 확인한 뒤 실행합니다.

출력의 `result=MATCH stage=COMPLETE`와 실제 `id`·`crc_rx`·`crc_expected`가 식별 결과입니다. `sleep=OK`는 검증 후 절전 명령도 수락됐다는 뜻입니다. `sleep=FAILED`는 제품 ID 확인에는 성공했지만 최종 센서 상태가 불명확함을 따로 나타냅니다.

`result=UNCONFIRMED`에는 실패한 `stage`와 원시 `operation_rc`가 표시됩니다. ID 응답 전 실패하면 ID·CRC는 `unavailable`로 남깁니다. 버스 초기화 실패는 `stage=BUS_INIT`, CRC 불일치는 `stage=CRC`, 다른 제품 ID는 `stage=PRODUCT_ID`로 구분합니다. 이 명령은 결과를 기록해 비교하기 위한 것이며 실패를 배선 불량으로 단정하지 않습니다.

## 결과를 해석할 때

일반 `i2cdetect`는 이 센서의 식별 시험과 다릅니다. 전용 조회는 버스 하나와 주소 `0x70`에만 접근하고, wake-up `0x3517` → 제조사 지정 대기 → read-ID `0xEFC8` → ID 2바이트와 CRC 1바이트를 읽습니다. 제품 ID 마스크 `(ID & 0x083F) == 0x0807`과 CRC가 모두 맞을 때만 SHTC3 계열의 통신 성공으로 판단합니다. 그때만 마지막 `0xB098` 절전 명령을 한 번 시도하며, 식별에 실패한 다른 `0x70` 장치에는 절전 명령을 추가로 보내지 않습니다.

성공 경로의 I²C 동작은 최대 4회로 고정되고, 주소 수나 관측 표본 수에 따라 늘어나는 순회가 없습니다. ACK를 포함한 117 SCL 클럭은 100 kHz에서 약 1.17 ms이며 두 300 µs 대기를 더한 공칭 합은 약 1.77 ms입니다. START/STOP·버스 경합·플랫폼 타임아웃·스케줄링·콘솔 출력을 포함한 최악 실행 시간은 보증하지 않습니다. 대기는 호출한 콘솔 태스크에서 수행하고 센서 work queue를 점유하지 않습니다.

제품 ID는 센서 계열 식별값이며 고유 일련번호가 아닙니다. 제품 ID·CRC 성공은 온습도 교정 정확도나 전원 품질을 보증하지 않습니다. 실패는 해당 단계에서 통신을 확인하지 못했다는 뜻이며 SDA/SCL 역결선·전원 부족·다른 버스·실물 모델 차이를 단독으로 판정하지 않습니다.

전송은 각 메시지에 100 kHz를 지정하고 NuttX의 기존 버스 잠금을 사용합니다. 전역 버스 속도 설정·명시적 `I2C_RESET`·오류 재시도는 호출하지 않습니다. 초기화와 해제를 짝지어 기존 차압계 드라이버의 버스 참조를 보존합니다. 이 플랫폼 계약은 해당 NuttX 소스로 확인했습니다. 이번 단발 검사에서는 같은 부팅 세션의 차압계 오류 증가가 없었지만, 모든 운용 조건에서 무간섭을 보증하는 시험은 아닙니다.

차압계와 공유하는 버스이므로 비행·시동 중 진단하지 않습니다. 진단은 전용 명령을 한 번 실행하는 방식이며 넓은 주소 범위를 반복 스캔하지 않습니다. 같은 SHTC3를 지속 드라이버와 단발 조회가 동시에 접근하지 않도록 해당 드라이버를 먼저 중지합니다.

## 설치·전원에서 유의할 점

이번 설치는 사용자 승인 후 보드 종류·펌웨어 메타데이터·체크섬을 대조하고 설정 백업과 공식 복원 이미지를 확보한 상태에서 완료했습니다. 다른 기체나 후속 업데이트에는 해당 보드와 파일이 일치하는지 다시 확인해야 합니다.

SHTC3 칩 자체의 공급 범위는 1.62–3.6 V이며, Pixhawk 포트 VCC를 그대로 쓸 수 있는지는 해당 모듈의 전원 회로에 달려 있습니다. 제품 ID·CRC 성공이 부적절한 공급 전압의 안전성을 보증하지는 않습니다. 전원이 분리된 상태에서 모듈 회로와 핀 순서를 확인하세요.

## PX4 원본을 업데이트할 때

기존 작업 트리를 reset하거나 다른 기준 버전의 패치를 섞지 않습니다. 새 체크아웃에서 이 전용 manifest로 `--check --allow-other-revision`을 실행하면 문맥 충돌 여부만 검사할 수 있습니다. API·보드 구성·빌드·메모리·실물 센서 호환성을 다시 검증하고 나서 기준 커밋과 파일 해시를 함께 갱신합니다. 제품 드라이버, 단발 진단 모듈, 원본 등록 패치를 분리한 구조를 유지합니다.
